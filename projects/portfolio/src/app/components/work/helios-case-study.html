01

The Organizational Problem

Penlink’s investigative products had evolved independently, each with its own visual language, interaction patterns, and engineering history. Growth through acquisition brought in products that were never designed to sit together.

Four designers worked across a product organization of more than 150 engineers. Consistency could not depend on reviewing every screen manually, and product development could not pause while a system was built.

The problem was how to make them feel familial without rebuilding them. The infrastructure had to be replaced without disturbing the product. Workflows customers already relied on had to keep working exactly as they were.

02

Building the Shared Foundation

Helios began as the Penlink Design System during a redesign of PLX Desktop, then expanded into distinct desktop and web modes within one Figma architecture. The original name survives in the code. Components carry a plds- prefix, and the migration to helios- was still in progress.

Shared decisions could vary by mode without being redefined component by component. The architecture had to be flexible enough for real differences, and firm enough to keep them exceptions.

Holding that balance took more than a component library. Structured Figma libraries connected to a production Angular library. That connection carried tokens, components, reusable product patterns, documentation, accessibility behavior, internationalization, and contribution workflows. The layered token model translated primitive values into semantic meaning, then into component-level implementation. Figma variables and the SCSS files stayed aligned.

No existing tool would keep that alignment. Figma’s variable sync sat behind a plan tier the team did not have, and a third-party token tool was not funded. I created a skill that pulled the published variables through MCP and updated the token files, so the process ran the same way every time.

03

Product Needs Shaped the System

Helios did not develop separately from product work. PLX Web was already in feature development, so interim Angular components kept delivery moving while exposing the states, inputs, and behaviors the supported system needed.

Those requirements informed official Helios components that were completed, merged, versioned, and published. Product teams could then repoint to the supported implementation rather than rework active features.

Preparing Tangles for onboarding, following a major Angular upgrade, surfaced localization and right-to-left requirements. Meeting them before the team adopted meant the foundation was ready when they arrived. Desktop used the same Figma variables, although translating them into XAML remained manual because the UX team did not own that markup.

Feature work also revealed reusable patterns for timelines, filtering, notifications, data visualization, and geographic mapping. Those patterns could return to Helios instead of remaining one-off solutions.

Production code became research: product constraints improved Helios, and Helios returned those lessons as shared infrastructure.

The open question was whether the documentation itself was robust, not just the system behind it. Benchmarking answered it: reading what the leading systems publish for a single component, then deciding which of those expectations Helios should adopt. Carbon, Material 3, and Polaris set the reference, and comparing against them turned a vague sense of incompleteness into a list the team could act on.

04

Making Adoption Visible

A component dashboard gathered audits, live demos, playgrounds, documentation, readiness, publishing information, and product usage in one place. Adoption became something the team could track instead of estimate. Claude handled recurring repository scans. Those scans separated direct adoption candidates from similar implementations that needed design and API review.

When a product required behavior Helios did not yet support, the component contract gained properties so the product could adopt without a breaking change. The debt stayed in the system rather than disappearing into individual products. Paying it down was the system's work, and no product team carried that weight.

Review without another meeting

Designers evaluated components against shared design principles and the investigative workflow research, then used the resolved decisions to refine both the Figma components and production Angular code. Recorded discussions allowed Claude to capture agreed actions and reusable documentation while the team stayed present in the critique. Components returned to UX for final approval after implementation. That kept Figma intent and coded behavior connected.

05

Outcomes & Tradeoffs

Before Helios, engineers rebuilt the same components in every product. Matching an implementation to its design took days of design feedback per feature. The loop between design and engineering stayed clogged. Features shipped at whatever quality the remaining time allowed.

Afterward, that refinement happened once in a meeting that already existed. Designers stopped re-explaining the same design to developers and spent that time on the next user problem. Developers got that time back for backend work, not two pixels of padding and a wrong border color.

The system also gave the team a shared way to describe what a product needed to do, so requirements moved into prototype review instead of being written up separately.

The system was new enough that reach was the result worth reporting: a decision made in a UX critique arrived in production intact. A product team shipped a customer-facing release consuming the published Helios library, and those components carried the same decisions defined in Figma.

Working prototypes gave product, design, and engineering a shared artifact for building stakeholder support and clarifying product needs. In-house analysts and other users could walk through proposed workflows while the team refined the experience in real time.

The wider payoff was still ahead. Helios gave a four-person design team a supported path to carry reusable decisions across the product organization. Tangles was next, and the preparation was already underway.

Tradeoffs

→Consistency vs. product-specific needs. Shared foundations had to leave room for genuinely different investigative workflows.

→A clean system vs. incremental adoption. Rebuilding every product was not realistic with 150+ engineers actively shipping, so Helios coexisted with legacy UI.

→Coverage vs. quality. The four-person team prioritized high-reuse foundations rather than systematizing every interface.

→Control vs. team autonomy. Governance needed enough structure to preserve coherence without making Helios a bottleneck.

→Automation vs. human judgment. Claude reduced repeated scanning and documentation work, while product logic, accessibility, responsive behavior, and edge cases remained human decisions.

The value of Helios was not the size of its library. It was the ability to make a design decision once, verify it in production code, and give many teams a supported foundation to build from.

06

What Came Next

Helios answered a question about duplication between products. Working on it raised another one: if the system already defines the components, tokens, states, and contracts, how much else can be built directly from it?

Orbit was the attempt to answer that. A separate workspace for working through a feature with Claude as a partner across the whole effort rather than one session at a time, with the work saved between sessions so nothing had to be re-explained, and a prototype as the output.

The point was what the prototype was made of. Assembled from published Helios components, it can only do what the system actually supports, so it cannot promise behavior that does not exist. When someone had to build something locally to finish an idea, that marked a gap in the system, and it came back as a contribution. Prototypes could draw on Helios directly or on local components made while exploring, which kept the difference between the two visible.

We started building it. It did not ship.

It is recorded here because the direction is the part worth keeping. A design system earns its cost when a decision made once keeps paying out, and this was an attempt to find how much further that could go. A fuller write-up of Orbit is coming soon.
