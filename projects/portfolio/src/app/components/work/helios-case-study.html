01

The Organizational Challenge

Penlink’s investigative products had evolved independently. Each product carried its own visual language, interaction patterns and engineering history. Growth through acquisition brought those differences into one portfolio, even as analysts moved between products during the same investigation.

Four designers supported a product organization of more than 150 engineers. Consistency could not depend on the design team reviewing every screen, and product development could not pause while a system was built.

The challenge was not to make every product identical. Evidentiary investigation and open-source lead generation had genuinely different requirements. Helios needed to establish a shared foundation while preserving the distinctions that mattered to the work.

02

Building the Shared Foundation

Helios began with the component work created during the PLX Desktop redesign. I expanded that foundation into shared desktop and web modes within one Figma architecture, then connected it to a production Angular library.

The architecture let common decisions remain common while supporting differences between platforms. Primitive tokens supplied the base values. Semantic tokens gave those values meaning. Component tokens applied them to specific controls and states. Figma variables and SCSS followed the same structure.

Penlink’s tooling could not automatically keep the published Figma variables and token files aligned. The native synchronization required a plan the organization did not have, and a third-party token tool was not funded. Without that higher Figma plan, I downloaded the variables from Figma manually and wrote a Claude skill that moved them into the token files the same way every time.

I was the sole developer of the Helios Angular component library. The component and system designs were collaborative work with the product design team. Christian Natis, Head of Canadian R&D, built the CI/CD workflow and advised me on backend integrations.

The production library was versioned and published for product teams. Component contracts covered more than appearance. They included behavior, responsive rules, accessibility, internationalization, right-to-left support and migration guidance.

Accessibility as infrastructure

Accessibility requirements were documented in Figma and carried into the production components. I conducted a formal internal audit against WCAG 2.1 AA, supported by scripted and manual component testing.

The audit did not produce a significant remediation list because accessibility had been considered during component design and implementation. That was preventative design and validation, not a claim of external certification or zero defects.

03

Product Work Shaped the System

Helios did not develop separately from product delivery. PLX Web was already in active feature development, so interim components kept the work moving while exposing the states, inputs and behaviors the shared system needed.

When a product required something outside the existing library, the design team did not automatically reject the difference or add a new component. We asked why the design diverged, whether an existing component could support the need and what requirements a shared solution would need to satisfy.

The product designer continued developing the feature while regular UX reviews surfaced those decisions early. I could begin the Angular implementation from the draft component instead of waiting for a final handoff. Production constraints then refined the component, and I carried the settled decisions back into Figma.

This created a bidirectional loop between product work and the shared system.

Feature work also revealed reusable patterns for timelines, filtering, notifications, data visualization and geographic mapping. Those patterns could return to Helios instead of remaining isolated product solutions.

Preparing Tangles for adoption after its Angular upgrade exposed requirements for localization and right-to-left support. I added that foundation before migration began. Tangles was not yet a production consumer when I left, so it belongs in the adoption-planning story rather than the production count.

Desktop teams used the same Figma library, shared tokens and specifications. Roughly 30 PLX Desktop engineers translated those decisions into XAML. The UX team did not own the XAML implementation.

04

Documentation as Operational Infrastructure

Documentation was created alongside each component, not after the implementation was finished.

A mature component page could include anatomy, hierarchy, states, responsive behavior, accessibility, microcopy, examples, API details, deprecations and migration guidance. Live demos used the published component. Props were read from the component source. Contrast values came from the active tokens.

That connection reduced the parts of documentation most likely to drift from production.

I directed Claude to help assemble and maintain the documentation, scan repositories and structure repeated information. I decided the documentation model, reviewed the output and made the product, accessibility and system decisions. Claude reduced repeated production work. It did not replace design judgment.

I benchmarked the documentation against Carbon, Material 3 and Polaris. The comparison turned a general sense of incompleteness into a visible roadmap. Gaps remained visible instead of being hidden to make Helios look more mature than it was.

05

Adoption Without Making the System a Bottleneck

PLX Web and PLX Connect adopted published Helios components primarily through the documentation and tooling. I collaborated with the teams when needed, but the goal was a self-service path that did not make me the implementation bottleneck.

I built a dashboard that brought component audits, demos, documentation, readiness, publishing status and repository usage into one place. Claude-assisted scans helped identify possible adoption candidates and separate direct replacements from implementations that still required design or API review.

The adoption inventory mapped existing product controls to likely Helios equivalents. It did not represent completed migrations or final API contracts. Product teams still needed to choose where to begin. Exact mappings would then be defined and tested one component at a time.

When a component was ready, I published a new package version. An automated “What’s New” message used the changelog as its source and posted updates to the Helios Microsoft Teams channel.

The system also made exceptions visible. If a product needed unsupported behavior, that need could become an intentional contract change or a tracked contribution instead of disappearing into one product’s codebase.

06

Outcomes and Tradeoffs

Helios carried shared design decisions into real product work.

The shared Figma library reached more than 150 developers across the organization. Roughly 30 desktop engineers used its tokens and specifications while building XAML interfaces. Roughly 10 developers and QA consumed the Angular component library through PLX Web and PLX Connect.

Those are different levels of adoption. The strongest result was not one large reach number. It was a governed system working across design, desktop specifications and published web components.

Before Helios, designers repeatedly explained the same decisions while engineers rebuilt similar controls in different products. With Helios, more of that refinement happened once at the shared-component level. Product teams gained supported implementations, and the design team could spend more time on the next workflow problem.

The system was still growing. Tangles had not completed adoption. Automated component-test coverage was maturing. The exact API mappings for broader migrations had not been finished. Helios coexisted with legacy interfaces because stopping product development for a clean rebuild was not realistic.

Tradeoffs

→Consistency versus product-specific needs. Shared foundations had to preserve meaningful differences between evidentiary and exploratory investigative work.

→System quality versus coverage. A four-person design team prioritized high-reuse foundations rather than attempting to systematize every interface.

→Incremental adoption versus a clean rebuild. Existing products continued shipping while the new foundation was introduced.

→Automation versus human judgment. Claude reduced repeated scanning and documentation work. Product logic, accessibility, responsive behavior and edge cases remained human decisions.

→Direct stewardship versus distributed ownership. My direct review kept Helios coherent while it was growing, but it also concentrated system knowledge and momentum. Given another pass, I would build broader sponsorship and direct engineering partnerships earlier so the system did not depend too heavily on one leadership relationship.

The value of Helios was not the size of its library. It was the ability to make a design decision once, verify it in production code and give multiple teams a supported foundation to build from.

07

What Came Next

Helios made component code and its usage intent legible to both people and AI agents.

I created agent guidance that described the available components and the rules for applying them. The clearest demonstrated use of that guidance was Orbit, a separate internal workspace for AI-assisted prototyping.

Orbit pulled from published Helios components before generating anything new. That improved component selection, variant accuracy, layout and brand alignment while helping designers reach convincing prototypes faster.

When a prototype required something outside Helios, Orbit scaffolded the unresolved interface and flagged it for review. The design team could decide whether the prototype should align with an existing component or whether the need belonged in the shared system.

This created another feedback loop:

Orbit was used by five UX team members across multiple prototype workspaces. Its prototypes supported internal research and subject-matter validation, but they were not shipped customer products.
