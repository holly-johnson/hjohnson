AI-Assisted Product Development · 2025–2026

Orbit

A shared workspace for building and testing AI-assisted prototypes.

As AI-assisted prototypes multiplied, their prompts, links, documentation and feedback risked becoming scattered across tools and individual designers.

I designed and built Orbit as a shared workspace that helped the UX team organize, build, version and test prototypes. Each feature kept its problem, supporting material, working prototype and feedback together. The prototypes were built in code from published Helios components.

Role
Designed and built Orbit end to end, including guided intake, workspace structure, live prototype experience, version-control workflow, designer-facing skills and release flow.
Users
Five UX team members used Orbit across multiple prototype workspaces.
Outcome
A developer-grade, version-controlled prototyping workflow that designers could use while retaining control over what was committed and shared.
Maturity
A working internal tool used on real feature work. Its prototypes were not shipped customer products.
01

A New Practice Created a New Problem

Penlink leadership asked teams to explore how AI could improve their work. The UX team identified prototyping as the most useful place to begin.

As more designers created AI-assisted prototypes, a practical problem appeared. Prompts, feature context, screenshots, links and feedback could easily become scattered across chat histories, repositories and individual machines.

The prototype itself was only one part of the work. Someone returning later also needed to understand:

  • →What problem the feature addressed
  • →What evidence supported it
  • →Which questions remained open
  • →What decisions had already been made
  • →Where the current prototype lived
  • →What feedback it had received
  • →How the work had changed over time

Orbit was built to preserve that complete record.

The goal was not another place to store prototype links. It was to keep the context and learning around each prototype intact so the team could find, understand and continue the work.

02

One Workspace for the Whole Feature

Orbit called each feature workspace a mission.

A guided intake prompted the designer for the problem statement, available evidence, requirements, risks, open questions and supporting documentation.

Submitting the intake created two connected things:

  • →A structured workspace in Orbit
  • →A corresponding branch in Azure DevOps for the prototype code

The Orbit workspace held the problem, documentation, screenshots, feedback, changelog and live prototype link. The branch held the version-controlled source.

This connected lightweight UX documentation to a real code workflow from the beginning.

Storage was initially structured as JSON files, with one folder for each workspace. That was enough to prove the model and expose the next requirement. By the time I left, the team had concluded that the files needed to become a real database.

That limitation was a sign of useful maturity. Orbit had progressed far enough for its proof-of-concept storage model to become the next constraint.

03

Designers Directed the Build

Designers opened Orbit in the browser alongside Claude Code.

Orbit organized and surfaced the feature context. Claude Code performed AI-assisted code changes under the designer’s direction.

The distinction matters. Orbit was not the generative model or an autonomous coding agent. It was the shared workspace that gave the designer and Claude Code a persistent, structured feature record to work from.

The designer remained responsible for the problem, requirements, interaction decisions and quality of the result. Claude Code accelerated implementation and helped maintain the working prototype.

I created skills that made the developer workflow usable without requiring every designer to perform the underlying commands manually. Designers could direct the commit, push and deployment process while still choosing when the work was ready to share.

The workflow gave designers access to version control and deployment without hiding the fact that those systems existed.

04

Helios First, Then Exceptions

Orbit pulled from published Helios components before generating anything new.

That constraint made the prototypes more credible. A mockup can imply any behavior. A coded prototype built from production components is limited by what the system actually supports.

The Helios agent guidance helped Claude Code select components, use their variants more accurately and keep layouts aligned with the brand.

When Helios could not supply what the feature needed, Orbit scaffolded the unresolved interface separately and flagged it in the workspace.

That exception became visible to the UX team.

The team could determine whether:

  • →An existing Helios component should have been used
  • →The design should align with a supported pattern
  • →The product had exposed a legitimate system gap
  • →A new or expanded component should enter the normal Helios process

The resulting loop was:

Helios-first prototype → flagged exception → UX review → alignment or shared-component contribution → publication through Helios

Rapid experimentation did not have to create invisible one-off debt. Exceptions became input to design-system governance.

05

From Feature Workspace to Shareable Prototype

Creating a feature workspace also created its branch.

When the designer chose to share changes, the designer-facing skill committed and pushed the work to that branch. CI/CD rebuilt the prototype and updated its live link in Orbit.

The designer controlled when that happened. AI assistance did not remove the decision to commit or publish work.

The refreshed prototype could then be opened by collaborators across time zones.

Orbit supported asynchronous feedback inside the workspace, but the higher-value use was often a live walkthrough. A designer or product partner could guide someone through the interactive prototype and gather feedback against real behavior rather than a static sequence of screens.

Orbit shortened the path from an idea to something testable and shareable. It did not reduce the work to faster screen production.

06

Research and Collaboration

Orbit prototypes were used during internal research and subject-matter validation.

I used one prototype with internal users while researching an active product feature. Other designers also gathered feedback from internal users, including analysts.

These were not external customer studies. The feature stays unnamed here to protect confidential product work.

The prototype gave participants something concrete to react to. The workspace preserved the problem, feedback and decisions around that prototype so the learning did not remain with the person who conducted the session.

Training and technical-writing partners could also access the current experience before release. That gave them more time to understand the feature intent and prepare supporting material.

Orbit supported both synchronous learning through walkthroughs and asynchronous collaboration through a shared, current prototype.

07

Adoption and Ownership

Five UX team members were using Orbit when I left. They created and maintained workspaces for their own prototype work.

Product-manager participation was part of the intended direction, but product managers had not yet started using it.

The UX manager directed a product-suite-aligned navigation, which I implemented before leaving. The rest was mine: I designed and built Orbit’s intake, workspace model, live prototype experience, DevOps workflow, designer skills and release flow.

Orbit was a working internal tool, not a formal launch or an organization-wide rollout.

Its demonstrated adoption was five UX team members using it across multiple prototype workspaces.

08

Outcomes and Tradeoffs

Orbit made a developer-grade workflow usable by designers while preserving intentional control over the work.

It connected:

  • →Guided feature intake
  • →Persistent documentation
  • →Version-controlled prototype code
  • →Published Helios components
  • →Automated deployment
  • →Interactive review
  • →Feedback and change history

The strongest outcome was continuity. A feature’s problem, implementation and learning stayed together instead of being scattered across people and tools.

09

Where It Was Headed

The next step was broader, sustained use.

More designers needed to take more features through the complete workflow. That volume would reveal where the intake, storage, review and deployment model needed to improve.

Product managers could eventually contribute feature context directly, but that remained an intended expansion rather than delivered adoption.

The JSON storage needed to become a database. The system also needed continued investment in Helios because prototype quality could not exceed the production foundation supplying it.

Orbit and Helios answered different questions.

Helios made a design decision reusable across products. Orbit explored how much more of a feature workflow could be built directly from that reusable system.

The lasting idea was smaller than “an AI workspace” and more useful: keep the problem, the working experience and the learning together so the team can continue the work without reconstructing its history.
